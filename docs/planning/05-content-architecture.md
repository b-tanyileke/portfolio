## Purpose

This document defines how information is organized and presented throughout the engineering website.

Rather than focusing solely on individual pages, it establishes how each piece of content contributes to a cohesive professional narrative. Every page, project, and engineering note should reinforce the same principles: clarity, evidence, reflection, and continuous growth.

---

## Content Philosophy

The website is designed to demonstrate engineering capability through evidence rather than claims.

Content should:

- Explain the problem before the solution.
- Show engineering thinking rather than only outcomes.
- Prioritize clarity over technical jargon.
- Connect related ideas across the website.
- Reflect continuous learning and professional growth.

Every piece of content should answer the question:
**"What does this help a visitor understand about the engineer?"**

---

## Audience Model

The website serves multiple audiences, each with different goals.

### Recruiters

Primary Questions:

- What does this engineer do?
- What technologies do they work with?
- Are the projects real?
- Where is the resume?
- How can I contact them?

Target experience:

- Answers available within two minutes.

---

### Hiring Managers

Primary Questions:

- How does this engineer approach problems?
- Can they communicate technical work?
- Do they demonstrate ownership?
- Do they reflect on trade-offs and decisions?

---

### Engineers

Primary Questions:

- How was this built?
- What architecture was used?
- Why were these technologies chosen?
- What challenges were encountered?
- What would they improve next?

---

### Future Self

The website should also function as:

- a career journal,
- a learning archive,
- a portfolio of engineering growth,
- a record of professional milestones.

---

## Content Hierarchy

Every major page should guide readers through a consistent progression.

1. Context
2. Problem
3. Motivation
4. Approach
5. Implementation
6. Evidence
7. Reflection
8. Future Work

---

## Project Narrative Framework

Every project begins with a narrative before discussing implementation.

The narrative should answer:

1. What problem was I trying to solve?
2. Why was this problem worth solving?
3. Why did I choose this approach?
4. What did I learn?

Only after this should technical implementation be introduced.

---

## Standard Project Structure

Each project page should follow a consistent structure.

1. Project Snapshot
2. Project Narrative
3. Problem Statement
4. Objectives
5. Solution Overview
6. Architecture
7. Technology Stack
8. Implementation
9. Challenges
10. Trade-offs
11. Results
12. Lessons Learned
13. Engineering Reflection
14. Future Improvements
15. Repository & Resources

---

## Engineering Reflection

Every project should conclude with a reflective section.

Suggested prompts:

- If I rebuilt this project today, what would I change?
- What assumptions proved incorrect?
- What was the most valuable lesson?
- Which decisions worked particularly well?
- What would I explore next?

Reflection demonstrates growth and engineering maturity.

---

## Evidence Model

Claims should be supported whenever possible.

Evidence may include:

- GitHub repositories
- Pull requests
- Architecture diagrams
- Screenshots
- Demonstration videos
- Benchmarks and metrics
- Documentation
- Test coverage
- Deployment links

---

## Cross-Linking Strategy

The website should encourage exploration by connecting related content.

Examples:

- Projects reference Engineering Notes.
- Engineering Notes reference Projects.
- Open Source contributions reference Projects.
- Skills reference supporting Projects.
- Resume entries reference detailed case studies.

Visitors should naturally discover deeper content as they explore.

---

## Content Maturity

Content may evolve over time.

Standard maturity states:

🌱 Idea

🚧 In Progress

🔄 Iterating

✅ Published

📦 Archived

These indicators communicate expectations to visitors.

---

## Writing Guidelines

Tone should be:

- Professional
- Honest
- Curious
- Reflective
- Precise
- Accessible

Avoid:

- Buzzwords
- Marketing language
- Unsupported claims
- Excessive self-promotion

---

## Success Criteria

The content architecture is successful if a visitor can:

- Understand what problems I solve.
- Follow my engineering process.
- Verify my work through evidence.
- Learn something from each project.
- See clear progression throughout my career.
